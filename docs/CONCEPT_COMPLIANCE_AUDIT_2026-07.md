# Аудит соответствия концепции — tax-advisor.ge / INFOHUB

**Дата:** 2026-07-04. **Стенд:** infohub-production (46.224.145.5), живой прод + код репозитория.

## Концепция (эталон для проверки)

Система даёт **точные ответы строго по загруженной базе** налогового законодательства Грузии и **судебных/третейских решений налоговых органов** (советы по спорам Службы доходов и Минфина, суды), и **строит статистику по этим решениям**, чтобы клиент мог выбрать стратегию разрешения налогового спора.

## Вердикт по осям

| Ось концепции | Вердикт | Кратко |
|---|---|---|
| 1. База законов + решений | **Частично соответствует** | Решения ингестируются массово (10,7 тыс.), покрытие источника 99,6%, но с 2026-06-27 ночной скрейпер пишет ненормализованные типы — новые решения невидимы для dispute-lane |
| 2. Ответы только по базе | **Частично соответствует** | Отказы и цитирование работают; но ~10 топовых фактов отдаются захардкоженным текстом в обход базы с приклеенной цитатой (relevance=1.0) |
| 3. Статистика по решениям | **Не соответствует** | Отсутствует полностью: ни извлечения исходов, ни агрегаций, ни UI |

## Ось 1. База законов и решений

### Что подтверждено на проде (SQL, 2026-07-04)

Всего: **14 793 документа / 269 988 чанков** (embedding 100%, embedding_v2 — 99,9%, 263 чанка в 24 док. без bge-m3).

Срез по типам (`SELECT document_type, count(*) ... GROUP BY 1`):

| document_type | Кол-во | Даты |
|---|---|---|
| court_decision | **10 734** | 2011 — 2026-04 |
| regulation | 1 687 | 2001 — ⚠ 2115 (1 битая дата) |
| law | 925 | 1984 — 2026 |
| news | 803 | |
| *сырые груз. метки (ненормализованные)* | **634** | все created_at ≥ 2026-06-27, date_published NULL |
| guideline и прочее | ~10 | |

Решения (`court_decision`) по органам: Служба доходов **6 164**, Минфин **4 282**, суды **214**. По годам: основной массив 2022–2026 (2023: 4 434; 2024: 3 010; 2025: 2 218; 2026: 671); до 2022 — единичные.

Сверка с источником: InfoHub API totals = 11 159 (NewDocument) + 3 627 (LegislativeNews) + 66 (Bill) = **14 852** против 14 793 в БД → разрыв ~59 док. (0,4%) — пропусков ингеста практически нет.

Ночной ингест: cron 03:00 ежедневно, прогон 2026-07-04 успешен (+15 док., exit 0), документы добавляются каждый день.

### Найденные дефекты

- **[КРИТИЧНО] Ночной скрейпер не нормализует document_type.** Все 634 документа, добавленные с 2026-06-27, лежат с сырыми грузинскими метками (`შემოსავლების სამსახურის დავების გადაწყვეტილება` — 281, `ფინანსთა სამინისტროს დავების გადაწყვეტილება` — 220, решения городского/апелляционного/верховного судов и др.) вместо `court_decision`/`law`/`regulation`, и с `date_published = NULL`. Следствие: **все новые решения по спорам (~501 шт. и растёт) невидимы** для dispute-lane retrieval (фильтр `document_type ILIKE '%court%'` в `backend/rag_v2/db_metadata_lookup.py:143`) и для будущей статистики. Причина: `backend/scraper/infohub_api_scraper.py` пишет сырое `type.name` из API, не прогоняя `infer_document_type()` из `corpus-tools/export_pipeline/infohub_exporter.py:241` (bulk-пайплайн это делает, ночной — нет).
- **[СРЕДНЕ] Алертинг ночного ингеста сломан**: `run_scraper.sh: line 39: /root/infohub/scraper_alert.sh: Permission denied` — Telegram-алерты не уходят с каждого прогона (нужен `chmod +x`).
- **[НИЗКО] Качество дат**: 640 документов с `date_published IS NULL`, 1 с датой 2115 г. Для статистики по годам даты обязательны.
- **[ПО ДИЗАЙНУ] Единственный источник — infohub.rs.ge.** Решения судов представлены только тем, что республикует InfoHub (214 судебных против 10,4 тыс. решений советов по спорам). Прямого ингеста court.ge / matsne.gov.ge нет. Для практики советов по спорам покрытие хорошее; судебная практика — фрагментарна.

## Ось 2. «Ответы только по базе»

### Что работает (живые проверки 2026-07-04, POST /public/query)

- Вне юрисдикции: «НДС в Армении», «налог на прибыль в США» → корректный отказ без источников (регрессия eval 2026-06-28 по США — исправлена).
- Несуществующая статья 9999 НК → «ответ не найден», ничего не выдумано.
- Несуществующий спор №99999/9/2024 → обоснованный отказ («не буду приписывать выводы другого дела»).
- Реальный спор №26773/2/2026 → найден именно этот документ (relevance 0.87), пересказ по содержанию.
- Цитаты собираются детерминированно из метаданных чанков, а не из свободного текста модели (`rag_v2/public_response.py:142-187`).
- Строгий системный промпт «СТРОГО по контексту, НИКОГДА из общих знаний» применяется ко всем ответам (`backend/rag/llm.py:147-170`).

### Найденные дефекты

- **[КРИТИЧНО ДЛЯ КОНЦЕПЦИИ] Захардкоженные ответы в обход базы.** На проде `INFOHUB_RAG_V2_AUTHORITATIVE` не задан → по умолчанию **включён** (`live_runtime.py:775`). Порог НДС 100k, эстонская модель, пенсия 2+2+2 и др. (~10 тем, `public_response.py:276-374`) отвечаются curated-текстом **до какого-либо поиска**, с приклеенной цитатой `TAX_CODE_SOURCE` и **relevance = 1.0** (отпечаток виден в живых ответах). Ответы фактически верные, но принципу «только по базе» не соответствуют: это позиции консультанта, зашитые в код, с цитатой, которая создаёт видимость retrieval.
- **[ВЫСОКО] Retrieval сам по себе обосновывает меньшинство фактов.** Собственный eval проекта (`evaluation/RAG_GROUNDING_PLAN.md:134-140`): `fact_correct` 39–40/40, но `fact_retrieval_correct` (чистый law-путь без костылей) — **13/40**. Свежий прогон харнесса: см. приложение ниже.
- **[СРЕДНЕ] `RAG_MIN_SIMILARITY=0.5` есть в конфиге (`core/config.py:73`), но не применяется** в v1-пайплайне — низкорелевантные чанки попадают в контекст. Faithfulness/entailment-проверки ответа нет.
- **[НИЗКО] Косметика отказов**: при отказе по ст. 9999 всё равно приклеивается «Источник: НК, статья 9999» (противоречивое сообщение); в отказ по фейковому спору утекает внутренний термин «live corpus».
- **[НИЗКО] Правила grounding в промпте только на русском**, ответы возможны на ka/en.

## Ось 3. Статистика по решениям

**Отсутствует полностью** — главный разрыв с концепцией:

- В схеме `documents` (`backend/models/document.py:26-56`) нет ни одного структурированного поля исхода: кто выиграл, оспариваемая статья НК, суммы, инстанция.
- Нет ни одного агрегирующего запроса/эндпоинта по решениям; `GET /api/v1/admin/stats` задокументирован (`docs/TECH_SPEC.md:163`), но не реализован; `GET /public/stats` возвращает лишь общий счётчик документов.
- Admin-дашборд — мок с хардкодом (`frontend/app/admin/page.tsx:93-142`); charting-библиотек в `frontend/package.json` нет; страницы аналитики нет.
- В роадмапе/доках статистика решений не упоминается.

При этом **сырьё для статистики есть**: 10,7 тыс. текстов решений с орг-принадлежностью и датами, dispute-lane retrieval, таксономия органов (`enhanced_scraper.py:36-42`), regex номера спора (`rag_v2/source_audit.py:8`).

## Дорожная карта (приоритизировано)

### П0 (гигиена, до всего остального)
1. **Починить нормализацию типов в ночном скрейпере**: прогонять `infer_document_type()` (и извлечение даты) в `infohub_api_scraper.py`; бэкфилл-миграция для 634 уже испорченных строк. Без этого деградирует и retrieval, и будущая статистика.
2. `chmod +x scraper_alert.sh` — восстановить алертинг.
3. Дочанковать/доэмбеддить 263 чанка без embedding_v2; исправить дату 2115.

### П1. Честный grounding
- Для каждого из ~10 захардкоженных ответов (`public_response.py:276-374`) найти в корпусе реальный подтверждающий документ и цитировать его (retrieval по known doc id), либо явно маркировать ответ «позиция консультанта, не найдено в базе». Убрать фиктивный relevance=1.0.
- Включить enforcement `RAG_MIN_SIMILARITY` перед сборкой контекста в v1.
- Убрать противоречивую цитату при отказе и жаргон «live corpus» из пользовательских сообщений.
- Скоуп узкий, по одному изменению с прогоном eval-харнесса (история откатов Phase B учтена; bge-m3 не трогаем).

### П2. Извлечение структурированных атрибутов решений (фундамент статистики)
- Таблица `decision_facts`: document_id, орган (Служба доходов / совет Минфина / суд+инстанция), номер и дата решения, тип спора (налог/таможня), оспариваемые статьи НК, суммы, **исход** (удовлетворено / частично / отказано), в чью пользу.
- LLM-экстракция (structured output) из `full_text` документов-решений; бэкфилл ~10,7 тыс. + шаг в ночной ингест.
- Валидация вручную на выборке 30–50 решений, целевая точность исхода ≥90%.

### П3. Статистика для клиента
- Backend: `backend/api/routes/analytics.py` — агрегации по `decision_facts` (доля удовлетворённых жалоб по статье НК / типу спора / органу / году).
- Frontend: страница аналитики (`frontend/app/admin/analytics/page.tsx`, пункт в `admin/layout.tsx:17-21`), recharts; далее публичная витрина.
- Чат: для вопросов класса `dispute_practice` дополнять ответ сводкой «по статье X за 2023–2026: N решений, из них M в пользу налогоплательщика».

### П4 (опционально)
- Прямой ингест court.ge / matsne.gov.ge, если фрагментарность судебной практики (214 док.) окажется значимой для клиентов.

**Результаты разведки П4 (2026-07-04):** живой программно-доступной картотеки судебных решений в публичном доступе Грузии нет:
- temida.court.ge и prg.supremecourt.ge — недоступны;
- info.court.ge — поиск только по известному номеру дела/штрихкоду (`/FinalDocument/FinalDecisionDocument`), каталога нет — массовая выгрузка невозможна;
- tcc.court.ge — только пресс-релизы;
- supremecourt.ge — 97 месячных PDF-сборников административной практики 2013–2017 (публикация прекращена);
- matsne.gov.ge — работает (консолидированные редакции, у НК v244), но НК и Таможенный кодекс уже есть в корпусе через InfoHub — ингест дублировал бы имеющееся.

**Сделано:** разовый импорт 97 сборников ВС (`backend/scripts/import_supreme_court_digests.py`; легаси-кодировка AcadNusx конвертируется в юникод; `metadata.kind='digest'`, из экстракции decision_facts сборники исключены — статистика остаётся по-решенчной).

**Рекомендации для полного покрытия судебной стадии:** официальный запрос открытых данных в ВСЮ/суды (решения публичны по закону), либо коммерческие правовые базы; точечная подгрузка дела по номеру через info.court.ge возможна, если клиент приносит номер дела.

## Приложение А. Свежий прогон eval-харнесса (2026-07-04)

`evaluation/eval_harness.py`, 43 вопроса, внутри infohub-backend (сырой JSON: `evaluation/results_2026-07-04.json`):

| Метрика | Результат | Смысл |
|---|---|---|
| fact_correct | **40/40** | ответы фактически верны |
| fact_sourced | 40/40 | у всех есть источник |
| fact_grounded | 36/40 | факт присутствует в найденных чанках (не grounded: vat_threshold_ka, import_vat_rate и 2 др.) |
| fact_retrieval_correct | **13/40** | ответ обоснован чистым retrieval без костылей — главный разрыв |
| refusal_correct | 3/3 | offtopic / фейковая статья / налог США — корректные отказы |

Вывод: пользовательское качество (40/40) достигается за счёт curated-обходов и параметрических знаний LLM; сам retrieval обосновывает лишь ~1/3 фактов. Это количественное подтверждение вердикта «частично соответствует» по оси 2.
