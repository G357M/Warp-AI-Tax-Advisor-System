# План укрепления RAG и повышения точности поиска (2026-07)

Составлен 2026-07-11. Основа: eval-история `evaluation/` (Phase 0–5), Phase A/B
диагностика generation fidelity (2026-07-02/03), аудит концепции
(`docs/CONCEPT_COMPLIANCE_AUDIT_2026-07.md`).

## Где мы сейчас (проверено по коду 2026-07-11)

- Прод стабилен: старая модель эмбеддингов (paraphrase-mpnet, 768d) +
  translate-then-embed, full eval 40/40 **с 5 гардами** (порог НДС, эстонская
  модель, пенсия, имущество, туроператор) в `rag_v2/public_response.py`.
- bge-m3 (1024d) полностью посчитан в `document_chunks.embedding_v2`, флаг
  `INFOHUB_EMBEDDING_V2=0` после отката 2026-07-02 (реальная регрессия: micro
  ранжировал поправку-2014 выше статьи НК).
- **Корневой класс проблемы (Phase A):** десятки чанков НК упоминают одну тему;
  чанк с точной ставкой/дефиницией не гарантированно топ-1. Это одна общая
  проблема, а не 6 разных багов.
- **Три попытки Phase B (реранкер-сигналы, IDF, chunk-dedup в merger) — net

  уже-правильное предпочтение metadata_search над semantic_search. Следующая
  попытка — только tie-breaker внутри semantic-кандидатов одного документа.
- **Eval недетерминирован:** 37–40/40 на неизменном коде. Механизм — перевод
  запроса на грузинский при `LLM_TEMPERATURE=0.3`, кэш только в памяти процесса
  (`rag/llm.py`), каждый холодный процесс переводит заново и иногда промахивается
  мимо корпусной формулировки.
- `article_ref`/`point_ref` в чанках никогда не заполнялись — точная ветка
  генерации для `canonical_law_lookup` недостижима. Статейное чанкование
  (`processor/chunker.py:chunk_by_article`, `scripts/rechunk_primary_legislation.py`)
  написано, не запускалось.
- Новые активы, которых не было при прошлых попытках: `decision_facts` v2
  (11k решений: статьи, суммы, исходы, цепочки), `law_amendments`,
  `documents.subtype`, `citation_resolver`.

## Принципы (выстраданы Phase A/B — не нарушать)

1. **Ни одно изменение retrieval/rerank не едет в прод без двойного гейта:**
   full eval (`evaluation/eval_harness.py`) ≥ базлайна И multi-trial 10×
   fresh-process на contested-наборе (pit_rate, pit_rate_en, profit_rate_en,
   vat_rate_more, dividend, sb_threshold, art_lookup, micro). Одиночный прогон —
   не сигнал.
2. Воспроизводить только через `maybe_run_live_rollout`, никогда — руками
   собранный промпт.
3. Детерминированные каналы (article/citation/exact-doc резолверы,
   metadata_search) имеют структурный приоритет над semantic_search для
   lookup-запросов. Любой новый сигнал не должен уметь его опрокинуть.
4. Гарды снимаются по одному и только после multi-trial гейта. Честный отказ
   лучше уверенной ошибки.

## П0 — Детерминизм и непрерывное измерение (фундамент, ~1 сессия)

Цель: убрать шум, из-за которого нельзя отличить регрессию от невезения.

1. **Детерминированный перевод запроса:** `rag/llm.py:translate_to_georgian` —
   temperature=0 (только для перевода, генерацию не трогать) + **персистентный
   кэш переводов в Redis** (ключ = hash нормализованного запроса, TTL долгий).
   Эффект двойной: evals воспроизводимы, а живые повторные запросы пользователей
   всегда получают одинаковый (лучший) перевод → консистентность продукта.
2. **Self-diagnosing eval:** харнесс сохраняет в result JSON used_chunks,
   document_type, chunk_index, каналы — чтобы любая будущая регрессия
   диагностировалась по артефакту, без повторных раскопок.
3. **Закоммитить multi-trial инструмент** (`evaluation/multitrial_contested.py`,
   сейчас существует только как scratch на сервере) — 10× fresh-process на
   contested-набор, отчёт pass-rate по вопросу.
4. **Ночной канареечный мини-eval:** 8–10 вопросов (contested + по одному на
   каждый гард) через прод-API после ночного скрейпа, алерт в Telegram при
   падении ниже порога (инфраструктура алертов уже есть в scraper_alert.sh).
   RAG перестаёт «тихо гнить» между сессиями.

Гейт П0: три полных eval подряд с идентичным результатом (дрожь ушла).
Риск: temperature=0 может изменить сам базлайн переводов — прогнать full eval
до/после только этого изменения.

## П1 — Статейное чанкование первичного законодательства (главный структурный ход)

Цель: чтобы «статья = чанк» и точный резолв по номеру статьи стал основным
путём для lookup-запросов, а не удачей semantic search.

1. Прогнать `rechunk_primary_legislation.py` на law/regulation/guideline
   (~48k чанков): один чанк на «მუხლი N», `article_ref`/`point_ref` в metadata.
   **Секвенирование:** писать обе колонки эмбеддингов (старую 768d и v2 1024d),
   чтобы работало при любом положении флага; прогон на проде — detached, после
   него ночной скрейпер не деплоить до завершения.
2. После заполнения `article_ref` включается точная ветка
   `_generation_query` для `canonical_law_lookup` («сначала главное правило
   статьи») — проверить, что она реально достигается и помогает.
3. **Усилить точный канал:** citation_resolver уже парсит «ст. 189 / 189-ე
   მუხლი» из запроса — довести до прямого exact-match чанка по
   (документ=НК, article_ref=N). Для запросов с номером статьи semantic search
   становится подстраховкой, а не судьёй.
4. Понять и задокументировать split `_build_rollout_chunks` / `_fetch_doc_chunks`
   (Phase B показал, что hint-based fallback делает реальную работу — сейчас
   это неявное поведение, от которого зависит половина lookup-запросов).

Гейт П1: full eval ≥ базлайна, multi-trial contested без регрессий,
спот-чек цитат (чанк = целая статья, ссылка точнее).
Риск: перечанкование меняет базу под ногами у всех каналов — делать первым
из содержательных этапов, чтобы дальнейшие сравнения шли уже на новой базе.

## П2 — Реранкер, попытка 4: только tie-breaker (после П1)

Строго по уроку Phase B: chunk-content-сигналы (lexical overlap с локальным IDF,
repealed-penalty, definitional-boost) применяются **только для выбора между
semantic_search-кандидатами одного document_id** — сценарий, который Phase A
и диагностировал. Никаких аддитивных бонусов, способных изменить порядок
между каналами. Кросс-канальный порядок не трогаем вообще.

Гейт П2: multi-trial 10× по всем contested (особенно pit_rate/vat_rate_more,
которые убивались попытками 1–3) + full eval. При любой деградации — стоп,
не тюнить на месте.

## П3 — Снятие гардов по одному

После П1+П2 пробовать снимать 5 гардов по одному (начать с того, чей чанк
после статейного чанкования резолвится детерминированно — вероятно, порог НДС).
Каждый: снять → multi-trial 10× на его вопросы + canary-набор → full eval →
только потом следующий. Если тема не проходит — гард остаётся, это
осознанная позиция (честный отказ лучше галлюцинации), а не долг.

## П4 — Переоценка bge-m3 (последним, опционально)

Только после П1–П3, потому что статейное чанкование меняет и картину для
bge-m3 (его micro-баг — ранжирование поправки выше статьи НК — может уйти
или ослабнуть на статейных чанках).

1. Diagnostic-фикс micro-класса: prior на document_type=law / authority для
   `canonical_law_lookup` в v2-пространстве.
2. Прогон полного гейта (П0-инструменты) с флагом на **стейджинге процесса**
   (docker exec с env-override — предварительно убедиться, что код читает
   флаг: урок «фейкового первого теста» 2026-07-02).
3. Флип только при строгом превосходстве, с готовым откатом (одна env-строка).
   Если превосходства нет — закрыть вопрос bge-m3 и не возвращаться:
   embedding_v2 лежит бесплатно, старая модель работает.

## П5 — Точность поиска на страницах сайта (независимый трек, можно параллельно)

Пользовательский поиск (/news, /laws, /guides, диалог /disputes) — сейчас
`ILIKE '%q%'` по заголовку:

1. **pg_trgm** индекс + similarity-порог: устойчивость к опечаткам и грузинским
   словоформам (склонение «კანონში/კანონის» и т.п.).
2. **Кросс-язычный поиск:** русский/английский запрос → перевод через уже
   существующий translate_to_georgian (с кэшем из П0) → поиск по ka-заголовкам.
   Пользователь ищет «нормы потерь» — находит «დანაკარგების ნორმები».
3. Поиск и по `document_number` (уже есть в admin, добавить в /news).
4. (Опция) единый глобальный поиск по сайту поверх этого же механизма.

Гейт П5: ручной чек-лист из ~15 реальных запросов на трёх языках.

## Порядок и оценка

| Этап | Зависимости | Оценка | Ценность |
|---|---|---|---|
| П0 детерминизм + канарейка | — | 1 сессия | делает всё остальное возможным |
| П1 статейное чанкование | П0 | 1–2 сессии + прогон на проде | главный структурный выигрыш точности |
| П5 поиск по сайту | — (параллельно) | 1 сессия | видимая пользователю точность поиска |
| П2 tie-breaker реранкер | П1 | 1 сессия | добивает micro-класс |
| П3 снятие гардов | П1+П2 | по 0.5 сессии на гард | честный «только по базе» без костылей |
| П4 bge-m3 | П1–П3 | 1 сессия | опционально; решение по данным |

- Повторный скрейпинг court.ge/temida (П4 аудита: программного доступа нет).
- Флип bge-m3 «на пробу» без полного гейта.
- Доверие одиночным eval-прогонам и `-e` env-override без проверки кода пути.
