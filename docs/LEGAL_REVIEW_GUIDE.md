# Инструкция для юриста: проверка фактов из судебных решений

Для кого: юрист, который проверяет данные аналитики налоговых споров на
tax-advisor.ge, и оператор, который передаёт ему таблицы и принимает их обратно.
Технические команды подробно описаны в `docs/PRODUCTION_OPERATIONS.md`, раздел
«Full unresolved decision-facts review»; здесь только то, что нужно для работы.

Главный принцип: система ничего не исправляет сама. Юрист проверяет запись по
официальному тексту решения и предлагает исправление; машина только сверяет,
что таблица заполнена корректно, и собирает список предложений. Применение
исправлений к базе — отдельный шаг с бэкапом и отдельным решением владельца.

## 1. Что проверяем

По каждому налоговому спору система автоматически извлекла факты: орган,
тип спора, исход, в чью пользу, номер и дату решения, оспоренные статьи, сумму.
Часть записей вызывает сомнение. Они собраны в две таблицы:

| Таблица | Что внутри | Объём (снимок `555749c`) |
|---|---|---|
| `review_items.csv` | Записи с сомнительными фактами | 192: 131 неясный исход, 39 нестандартных ссылок на статьи, 22 расхождения исхода |
| `duplicate_groups.csv` | Группы решений с одинаковым номером — возможные дубли | 463 группы, 946 решений |
| `duplicate_members.csv` | Состав каждой группы (только для чтения) | 946 строк |

Публичная аналитика использует только пригодные для подсчёта факты: записи с
неясным исходом в неё не входят. Проверка возвращает их в статистику и
уточняет остальные данные.

## 2. С чего начать

1. **11 приоритетных групп дублей.** Файл
   `duplicate_confirmation_queue.csv` в каталоге технической сверки: 1 группа,
   где официальные тексты полностью совпадают, и 10 — где совпадают на 95% и
   больше. Это самая быстрая и полезная часть.
2. **Записи с неясным исходом** (`queue_reasons` содержит `unclear_outcome`) —
   их больше всего, и именно они выпадают из статистики.
3. Остальные записи и группы — по мере возможности. Работу можно сдавать
   частями: незаполненные строки остаются в статусе `pending`.

## 3. Где лежат файлы (для оператора)

На сервере, каталог `/root/infohub/.state/` (доступ только root):

- `decision-facts-full-expert-review/<REVIEW_ID>/` — таблицы для проверки,
  `review_bundle.json` (эталон, не менять), `REVIEW_INSTRUCTIONS.md`;
  `duplicate_groups.technical-prefill-v1.csv` — таблица дублей, в которой
  уже заполнены технические доказательства (`evidence_locator`, `notes`);
- `infohub-duplicate-verification/<VERIFY_ID>/` — результат сверки с
  официальным API InfoHub, включая `duplicate_confirmation_queue.csv`.

Передача юристу — отдельное решение владельца. Файлы не должны попадать в Git,
мессенджеры с публичным доступом или общие папки.

Снимок данных сделан в августе 2026 года. Решения, загруженные позже, в него
не входят — их можно проверить следующим проходом после свежей выгрузки.

## 4. Как работать с таблицей

1. Откройте CSV в Excel и сохраните **копию** как `.xlsx`
   (например, `review_items.working.xlsx`).
2. Меняйте **только** редактируемые столбцы (перечислены ниже). Столбцы с
   данными записи (номер, дата, исход и т. д.) не трогайте: при импорте любое
   их изменение будет отклонено.
3. Вводите обычный текст. Формулы, макросы и ссылки на другие файлы запрещены —
   такой файл не будет принят.
4. Время — в UTC в формате `2026-11-02T10:15:00Z`.
5. Строку, проверку которой вы закончили, отметьте `review_state` = `complete`.
   Остальные оставьте `pending`.

## 5. Таблица фактов (`review_items`)

Для каждой проверенной строки:

| Столбец | Что заполнить |
|---|---|
| `review_state` | `complete` |
| `source_accessible` | Открылся ли официальный текст решения |
| `identity_correct` | Это то самое решение (номер, дата публикации) |
| `authority_body_correct` | Орган, рассмотревший спор |
| `dispute_type_correct` | Тип спора |
| `outcome_correct` | Исход |
| `in_favor_correct` | В чью пользу |
| `decision_number_correct` | Номер решения |
| `decision_date_correct` | Дата решения |
| `contested_articles_correct` | Оспоренные статьи |
| `amount_correct` | Сумма в лари |
| `evidence_locator` | Где подтверждение: ссылка на официальный текст и место в нём (раздел, абзац, страница). **Обязательно** |
| `proposed_corrections_json` | Исправления — только для полей с `incorrect` (см. ниже) |
| `legal_rationale` | Обоснование. **Обязательно**, если есть хоть одно `incorrect` |
| `confidence` | `high`, `medium` или `low` |
| `reviewer` | Ваше имя. **Обязательно** |
| `reviewed_at_utc` | Время проверки. **Обязательно** |
| `second_reviewer`, `second_reviewed_at_utc` | Второй проверяющий (см. правило ниже) |
| `notes` | Свободные заметки |

Значения для полей `..._correct`:

- `correct` — значение в таблице верное;
- `incorrect` — неверное, нужно исправление;
- `not_applicable` — к этому решению не относится (например, суммы нет);
- `unable_to_verify` — проверить невозможно.

**Исправления.** Для каждого поля с `incorrect` укажите правильное значение в
`proposed_corrections_json`, в формате JSON:

```json
{"outcome": "rejected", "in_favor": "authority"}
```

Допустимые значения:

- `outcome`: `satisfied` (жалоба удовлетворена), `partially_satisfied`
  (удовлетворена частично), `rejected` (отклонена), `unclear` (неясно);
- `in_favor`: `taxpayer` (в пользу налогоплательщика), `authority` (в пользу
  налогового органа), `partial` (частично), `unclear`.

Остальные поля (`authority_body`, `dispute_type`, `decision_number`,
`decision_date`, `contested_articles`, `amount_gel`) исправляются в том же
JSON. Если `identity_correct` = `incorrect`, можно исправить также
`document_number` и `date_published`. Исправлять поле, отмеченное как
`correct`, нельзя.

**Правила, которые проверит система:**

- если официальный текст недоступен (`source_accessible` = `unable_to_verify`),
  все остальные поля могут быть только `unable_to_verify` или
  `not_applicable` — подтвердить или опровергнуть значение без источника нельзя;
- исправление **исхода** или **«в чью пользу»** требует второго проверяющего:
  другого человека, со своим временем проверки.

## 6. Таблица дублей (`duplicate_groups`)

Состав группы смотрите в `duplicate_members.csv` по `group_id`. В
подготовленной таблице `evidence_locator` и `notes` уже содержат технические
данные сверки — их можно дополнить, но решение принимаете вы.

| Столбец | Что заполнить |
|---|---|
| `review_state` | `complete` |
| `duplicate_verdict` | `true_duplicate` — все документы группы одно и то же решение; `mixed_group` — часть дублирует друг друга, часть нет; `distinct_decisions` — разные решения с одинаковым номером; `unable_to_verify` |
| `canonical_document_id` | Для `true_duplicate` и `mixed_group`: `document_id` документа, который остаётся основным |
| `proposed_exclusions_json` | Для `true_duplicate` и `mixed_group`: список `document_id`, которые исключаются из статистики, например `["id-1", "id-2"]` |
| `evidence_locator`, `legal_rationale` | Обязательно |
| `confidence`, `reviewer`, `reviewed_at_utc` | Обязательно |
| `second_reviewer`, `second_reviewed_at_utc` | Обязательно для `true_duplicate` и `mixed_group` |

Правила:

- при `true_duplicate` в исключения входят **все** документы группы, кроме
  основного;
- основной документ не может быть в списке исключений;
- при `distinct_decisions` и `unable_to_verify` основной документ и исключения
  оставляйте пустыми;
- «исключение» не удаляет официальный документ — он остаётся в корпусе и
  только не считается в статистике второй раз.

## 7. Сдача работы (для оператора)

1. Загрузите заполненный `.xlsx` в каталог проверки на сервере с правами
   `0600`.
2. Запустите импорт таблицы — сначала проверочный прогон, затем запись с
   хешами из него (`import_decision_facts_review_workbook.py`, команды в
   `docs/PRODUCTION_OPERATIONS.md`). Для таблицы фактов используйте
   `--review-type review-items`, для дублей — `--review-type duplicate-groups`.
3. Проверьте результат валидатором `validate_decision_facts_expert_review.py`.
   Для промежуточной сдачи — без `--require-complete`: он покажет ошибки в
   заполненных строках и посчитает оставшиеся `pending`.
4. Ошибки валидатора вернуть юристу с номером строки (`review_id` или
   `group_id`) и текстом ошибки.

Когда все строки заполнены, валидатор с `--require-complete --execute`
формирует `correction_proposals.json` — список предложенных исправлений. Он
ничего не меняет в базе. Применение исправлений — отдельная доработка с
бэкапом, проверкой и решением владельца.

## 8. Исторические редакции законов

Это отдельная, более объёмная очередь: подтверждение того, какая редакция
статьи действовала на какую дату. Она описана в
`docs/TEMPORAL_LEGAL_EXPERT_REVIEW.md` и `docs/MATSNE_PUBLICATION_EDITIONS.md`.
Начинать её имеет смысл после очереди фактов и с одного закона — Налогового
кодекса.
