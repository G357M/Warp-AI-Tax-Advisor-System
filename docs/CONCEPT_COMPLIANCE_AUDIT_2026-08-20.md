# Аудит соответствия Modern Ecosystem — tax-advisor.ge

**Дата:** 2026-08-20. **Контур проверки:** локальный репозиторий, GitHub `main`, production `/root/infohub` на Hetzner и публичный домен `tax-advisor.ge`.

Этот документ заменяет июльский аудит как актуальный срез. Июльский файл остаётся историей изменений: его выводы про отсутствующую аналитику и меньший размер корпуса больше не описывают текущий production.

## Итог

`tax-advisor.ge` уже соответствует концепции как специализированная правовая система, а не универсальный чат: у неё есть собственный корпус, разделение нормативных и спорных материалов, ответы с детерминированным evidence-контрактом, аналитика решений и узнаваемый визуальный язык Modern Ecosystem.

До полного продуктового соответствия остаются не декоративные, а системные функции: автоматизированная коммерция, восстановление доступа, организации Business и постоянно измеряемое качество RAG. Поэтому общий вердикт — **сильная рабочая основа, частично завершённая продуктовая экосистема**.

## Что концептуально реализовано

### 1. Не «ответ из памяти модели», а юридический evidence contract

Публичные и авторизованные ответы возвращают структурированный статус доказательности. Контракт различает точную норму, документальную опору, неполную опору, недостаточность корпуса и вопрос вне грузинской юрисдикции. Статус формируется детерминированным кодом, поэтому интерфейс не называет ответ «проверенным», когда подтверждён только найденный источник.

На контрольных вопросах по НДС на русском, грузинском и английском система возвращала grounded-ответ со ссылкой на статью 166 Налогового кодекса; вопрос о налоге США был корректно классифицирован как `out_of_scope`.

### 2. Корпус стал продуктом, а не только внутренним индексом

Нормативный и dispute-пути разведены. Пользователь видит официальные источники, каталог законов, хронологию изменений и публичную аналитику решений. Структурированный слой `decision_facts` превратил тексты споров в фильтруемые данные по исходам, органам, статьям, суммам и цепочкам обжалования.

### 3. Пользовательский контур связан с реальным backend

Новая frontend-сессия хранится в `HttpOnly`, `Secure`, `SameSite=Lax` cookie. Free-квота списывается только за успешно обработанный вопрос. История Pro/Business сохраняет сам ответ и точный список источников; доступ к ней закрыт тарифным gate на backend, а не только спрятан в интерфейсе.

Тарифный текст теперь не обещает команду из пяти пользователей: такого механизма ещё нет. Это важно для принципа Modern Ecosystem — интерфейс сообщает только то, что действительно реализовано.

### 4. Визуальная система узнаваема и связана с Modern

Код следует `DESIGN.md`: чистый чёрный фон, liquid-glass как основной материал, сигнальный красный для источников и действий, цитатная планка, serif-курсив в display-ролях, sans в тексте и общий футер продуктов Modern. RU/KA/EN используют одну компонентную систему, а анимации учитывают `prefers-reduced-motion`.

Автоматическая проверка интерфейсных анти-паттернов прошла без замечаний, frontend lint/type-check/build успешны. Production-сборка проверена в реальном браузере на desktop и 390 px: семантическая структура сохранена, мобильное меню открывается и закрывается при навигации.

## Безопасность и поставка

- Production Python-зависимости обновлены и проходят `pip-audit` без известных уязвимостей.
- Убран уязвимый стек `python-jose`/`ecdsa`; JWT переведён на `PyJWT[crypto]`.
- Пароли проверяются напрямую совместимым bcrypt-форматом `$2b$`, а предел 72 UTF-8 bytes валидируется на API boundary.
- Frontend Docker image собирается детерминированно через `npm ci`, использует standalone Next output и непривилегированного пользователя.
- Backend использует `torch 2.13.0+cpu`; активный image по Docker inspect уменьшен с 3,163 ГБ до 492 МБ. Контрольный embedding и top-5 retrieval до и после перехода совпали побайтово.
- GitHub CI проверяет актуальные контракты, а не удалённые или несуществующие тестовые команды.
- Production CD оставлен ручным и использует pinned SSH host key; публичный health-check завершает поставку.

## Следующие этапы

### Выполнено — управляемая миграция frontend runtime

Next 14 / React 18 переведены на Next 16.3.1 / React 19.2.8 без `npm audit --force`. Удалён устаревший `next lint`, включены ESLint 9 flat config и `next typegen`; новые React hooks checks устранены через корректное управление состоянием и отмену устаревших запросов. Полный frontend dependency tree проходит `npm audit` без известных уязвимостей.

### Выполнено — JWT rotation и CPU-only ML runtime

Production JWT переведён на новый 256-bit ключ через ограниченное grace window:
новые сессии подписываются только текущим ключом, а старый принимается лишь до
явного UTC cutoff и затем удаляется финализатором с проверкой HTTP 401. Backend
переведён на официальный CPU-only PyTorch wheel без изменения модели,
размерности embedding или результатов контрольного retrieval.

### P1 — завершить коммерческий продукт

1. Email verification и password recovery.
2. Автоматизированная оплата, webhook и идемпотентное изменение плана.
3. Organizations, invitations, roles и seats для Business. Только после этого можно обещать командное использование.

### P1 — измерять юридическое качество постоянно

В CI уже добавлен версионируемый offline golden set по RU/EN/KA нормативным,
локальным и dispute-маршрутам. Он блокирует изменение при деградации
classification accuracy, top-1 locator recall, source-audit accuracy или exact
citation rate; дополнительно запускаются 111 существующих RAG v2 тестов и 110
matrix subtests. Этот слой детерминирован и не выдаётся за проверку живого корпуса.

На Hetzner после ночного скрейпера уже выполняется 10-вопросный live canary через
реальный pipeline; прогон 2026-08-20 дал `10/10`, а падение ниже порога отправляет
Telegram-alert. Ошибки вспомогательных post-ingest шагов теперь также агрегируются
в alert, а не маскируются `|| true`.

Дополнительно подготовлен отдельный deterministic live-corpus слой: 21 запрос
поровну на RU/EN/KA проверяет classification, top-1 документ/канал/locator и
source audit непосредственно через production PostgreSQL. Отчёт включает hash
набора, commit, fingerprint корпуса и метрики по каждому языку. Semantic/LLM
канал в этом прогоне запрещён, поэтому измерение воспроизводимо и не создаёт
скрытых API-расходов. Первый production baseline на `ea53af6` прошёл `21/21`:
classification, top-1 contract, source audit и минимальный языковой recall равны
`1.0`; в Git сохраняется только агрегированный allowlist без запросов и строк
по отдельным документам.

Поверх retrieval-слоя добавлен отдельный bounded answer-safety набор из 12
сценариев, поровну на RU/EN/KA: grounded VAT, другая юрисдикция, несуществующая
статья и очевидный off-topic. Он проверяет текстовый контракт, evidence status,
язык ответа, отсутствие опасной уверенности и минимальный результат по языкам.
Production baseline на `e52ecac` прошёл `12/12`, все метрики равны `1.0`; из
жёсткого потолка 12 потребовалось 6 фактических provider-вызовов. Полный отчёт
остаётся operational-only, в Git попадает только агрегированный allowlist.

После post-ingest maintenance nightly runner автоматически запускает два
read-only/no-LLM gate: 21-case live-corpus locator contract и decision-facts
quality contract. При non-zero exit, отсутствии агрегированной строки или
неполном mode-600 operational artifact отправляется Telegram-alert; успешный
прогон сообщений не создаёт. Provider-backed answer-safety остаётся ручным и
bounded.

Для передачи профильному эксперту добавлен bounded operational handoff:
детерминированная выборка покрывает каждую категорию аномалий, дедуплицируется в
стабильные review ID и материализуется только по точному числу строк и SHA-256
исходного mode-600 отчёта. Структурный контракт прошёл все пороги на 11 363
решениях, но намеренно не выдаёт это за юридическую верификацию выводов. Саму
проверку и её результаты должен выполнить и подписать профильный эксперт.

Для перехода от калибровочной выборки к полному закрытию очереди добавлен
отдельный read-only/no-LLM экспорт всех unresolved fact rows и всех участников
duplicate-number групп. Он разделяет машинную приоритизацию
`exact/likely/ambiguous` и юридический вердикт, формирует защищённые таблицы и
проверяет неизменность исходных колонок. Итог валидатора — только proposal-only
манифест; автоматического UPDATE/DELETE юридических данных намеренно нет.

Ручная duplicate-проверка дополнена bounded verifier официального InfoHub API.
Он автоматически сравнивает текущие нормализованные тексты и реквизиты,
сохраняя только fingerprints, similarity и metadata differences. Совпадение
становится кандидатом для пакетного подтверждения экспертом, но не юридическим
вердиктом; worksheet, proposal manifest и база автоматически не изменяются.

## Граница обещания продукта

Система помогает найти и объяснить релевантные грузинские правовые источники и практику. Она не должна представлять автоматически grounded-ответ как индивидуальное юридическое заключение, гарантировать исход спора или маскировать неполноту корпуса. Такой честный уровень обещания соответствует и юридическому риску продукта, и визуально-коммуникационной концепции Modern Ecosystem.
