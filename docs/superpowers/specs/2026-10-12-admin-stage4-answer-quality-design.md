# Админка, этап 4: качество ответов — дизайн

Дата: 2026-10-12. Статус: на согласовании.

## Контекст и цель

Этапы 1 и 2 (PR #20, #21, задеплоены) дали админке единый стиль, журнал
`admin_audit_log`, раздел клиентов и коды ошибок. О качестве ответов
админка пока ничего не знает:

- пользователи не могут оценить ответ;
- админ не может разметить ответ;
- признаки качества, которые считаются для каждого ответа
  (`attach_evidence`), уходят только в ответ API и не сохраняются;
- тексты диалогов вошедших пользователей хранятся в `messages`, вопросы
  гостей (`/api/v1/public/query`) не хранятся.

Этап 4 — третий по порядку из пяти (1 основа → 2 клиенты → **4 качество
ответов** → 3 динамика → 5 операции). Он даёт Геле очередь плохих ответов,
инструмент их разметки и сигнал от пользователей. Сводка этапа станет
исходными данными для этапа 3.

### Успех этапа

- Каждый новый ответ вошедшему пользователю сохраняется вместе с
  признаками качества и временем ответа.
- Вошедший пользователь может поставить 👍/👎 (с необязательным
  комментарием) любому ответу в своих диалогах, изменить или снять оценку.
- В админке есть лента ответов с фильтрами и очередью «👎 без разметки».
  В ленте пользователи показаны псевдонимами.
- Админ размечает ответ вердиктом и причинами. История разметки
  сохраняется, каждая разметка попадает в журнал.
- Раскрыть, кто задал вопрос, можно только отдельным действием с причиной
  и записью в журнал.
- Политика конфиденциальности (RU/KA/EN) называет проверку качества
  ответов целью обработки и оценки ответов — категорией данных.

### Решения, принятые с пользователем

- Состав: лента диалогов, оценка от пользователей, разметка админом,
  сохранение признаков.
- Приватность: псевдонимы в ленте, раскрытие пользователя с записью в
  журнал, дополнение политики конфиденциальности.
- Оценки ставят только вошедшие пользователи. Гостевые вопросы не
  сохраняются и не оцениваются.
- Хранение — вариант A: новые таблицы `answer_ratings` и `answer_reviews`,
  новые колонки `messages.evidence` и `messages.processing_ms`, один
  дополнительный скрипт схемы с закреплённой контрольной суммой, который
  запускается из `deploy_production.sh`.
- Порог «долгого ответа» — 30 секунд. Лимит изменений оценок — 60 в час на
  пользователя. Раскрытие пользователя доступно из любого ответа.

### Вне этапа 4

- Оценки и сохранение гостевых вопросов.
- Графики динамики во времени (этап 3). На этом этапе есть только сводка за
  период.
- Автоматическая оценка ответов моделью (LLM-as-judge), повторная
  генерация ответа из админки, правка корпуса из админки.
- Экспорт выборки во внешние файлы.
- Фильтр ленты по языку: язык запроса сейчас не хранится.
- Пересчёт признаков для старых ответов: у них признаков нет, они
  показываются как «нет данных».
- Логика RAG, маршрутизации и генерации не меняется. Меняется только
  сохранение результата.

## 1. Схема

Новый скрипт `backend/scripts/add_answer_quality.py`. Он устроен как
`add_admin_audit_log.py`:

- только добавляет объекты;
- без `--apply` выводит план, с `--apply` применяет;
- повторный запуск ничего не меняет;
- `contract_sha256()` по тексту DDL закреплена в `scripts/deploy_production.sh`
  как `ANSWER_QUALITY_SCHEMA_CONTRACT_SHA256`;
- деплой запускает его с `--apply --expected-contract-sha256` до старта
  бэкенда, сразу после шага журнала.

| Объект | Определение |
|---|---|
| `messages.evidence` | `JSONB NULL` |
| `messages.processing_ms` | `INTEGER NULL`, `CHECK (processing_ms IS NULL OR processing_ms >= 0)` |
| `answer_ratings` | `id UUID PK`, `message_id UUID NOT NULL REFERENCES messages(id) ON DELETE CASCADE`, `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`, `value SMALLINT NOT NULL CHECK (value IN (-1, 1))`, `comment TEXT NULL CHECK (char_length(comment) <= 1000)`, `created_at`, `updated_at TIMESTAMP NOT NULL`, `UNIQUE (message_id)` |
| `answer_reviews` | `id UUID PK`, `message_id UUID NOT NULL REFERENCES messages(id) ON DELETE CASCADE`, `reviewer_id UUID NOT NULL` (без FK, как `actor_id` в журнале), `verdict VARCHAR(16) NOT NULL CHECK (verdict IN ('correct','partial','wrong'))`, `reasons TEXT[] NOT NULL DEFAULT '{}'`, `note TEXT NULL CHECK (char_length(note) <= 2000)`, `created_at TIMESTAMP NOT NULL` |
| Индексы | `ix_answer_reviews_message_created (message_id, created_at)`, `ix_answer_ratings_value (value)`, `ix_messages_role_created (role, created_at)` |

- `UNIQUE (message_id)` в `answer_ratings` означает одну оценку на ответ.
  Это корректно, потому что ответ принадлежит одному пользователю, автору
  диалога.
- Разрешённые значения `reasons` проверяются в API: `not_in_corpus`,
  `wrong_version`, `wrong_citation`, `fabricated`, `incomplete`,
  `language`, `other`. CHECK на массив не ставится, чтобы позже добавлять
  причины без изменения схемы.
- `answer_reviews` защищается от UPDATE, DELETE и TRUNCATE таким же
  триггером, как журнал (`answer_reviews_immutable`). Удаление сообщения
  каскадно удаляет его разметку, поэтому триггер разрешает DELETE, только
  если сообщения больше нет. Если такое условие окажется ненадёжным, при
  написании плана выбирается более простая защита. Решение записывается в
  план.
- Удаление пользователя каскадно удаляет его диалоги, сообщения и оценки.
  Разметка удаляется вместе с сообщением. Журнал сохраняется, как и раньше.
- ORM-модели: `Message.evidence`, `Message.processing_ms`, новые
  `AnswerRating` и `AnswerReview` в `backend/models/`.

## 2. Сохранение при ответе

В `POST /api/v1/query` (`backend/api/routes/query.py`):

- При сохранении ответа ассистента записываются:
  - `evidence` — словарь из `result["evidence"]` (`status`, `basis`,
    `coverage`, `question_class`, `source_count`, `official_sources_only`,
    `has_precise_citation`, `has_official_provision_link`, `generated_at`)
    плюс `retrieved_count`;
  - `processing_ms` — целые миллисекунды от начала обработки запроса до
    сохранения.
- В ответ API добавляется `message_id` (UUID ответа ассистента). Для этого
  сообщение получает id до коммита (`db.flush()` или явный `uuid4()`).
- `QueryResponse` получает поле `message_id: Optional[UUID]`. На гостевом
  `/public/query` оно отсутствует или равно `null`.
- Ошибка генерации ведёт себя как раньше: откат и возврат квоты.

`GET /api/v1/query/conversations/{id}` добавляет у каждого сообщения
ассистента поле `rating: {value, comment} | null` — текущую оценку
пользователя.

## 3. Оценка пользователя

- `PUT /api/v1/query/messages/{message_id}/rating`, тело
  `{value: 1 | -1, comment?: string ≤ 1000}`. Создаёт или заменяет оценку.
  Ответ: `{value, comment}`.
- `DELETE /api/v1/query/messages/{message_id}/rating` снимает оценку,
  ответ 204. Если оценки нет, ответ всё равно 204.
- Требуется `get_current_user`.
- Сообщение не найдено или принадлежит чужому диалогу → 404
  `message_not_found`.
- Сообщение пользователя, а не ассистента → 409 `not_assistant_message`.
- Лимит: не больше 60 PUT/DELETE в час на пользователя, ключ в Redis
  `rating:{user_id}:{YYYYMMDDHH}`. Превышение → 429 `rating_rate_limited`.
  Если Redis недоступен, лимит не применяется.
- Пустой комментарий или комментарий из пробелов сохраняется как `NULL`.
  Комментарий длиннее 1000 символов → 422.
- В журнал админа оценки не пишутся: это действие пользователя, а не
  админа.

## 4. Админка: API

Новый роутер `backend/api/routes/admin_quality.py`, префикс
`/admin/quality`, зависимость `require_admin` на уровне роутера. Ошибки
передаются через `admin_error` с `{code, message}`, у каждого маршрута
литеральный `responses={…}`, никакого SQL в f-строках.

### 4.1. Псевдоним

`pseudonym(user_id) = "U-" + HMAC_SHA256(SECRET_KEY, str(user_id)).hexdigest()[:6].upper()`.
Псевдоним стабилен, по нему нельзя восстановить id. Возможная коллизия на
шести символах допустима: псевдоним служит меткой, а не ключом.

### 4.2. `GET /admin/quality/answers`

Строка ленты — ответ ассистента вместе с предшествующим ему вопросом
пользователя из того же диалога (ближайшее более раннее сообщение с
`role='user'`).

| Параметр | Значения |
|---|---|
| `period` | `7d` (по умолчанию), `30d`, `90d`, `all` |
| `rating` | `up`, `down`, `none` |
| `verdict` | `unreviewed`, `correct`, `partial`, `wrong` (по последней разметке) |
| `flags` | можно повторять: `no_precise_citation` (`evidence->>'has_precise_citation'` не true), `no_sources` (`source_count = 0`), `not_grounded` (`status` ≠ `grounded`), `slow` (`processing_ms > 30000`), `no_evidence` (`evidence IS NULL`) |
| `q` | до 200 символов: ILIKE по тексту вопроса, с экранированием `%`, `_` и `\` |
| `limit`, `offset` | 1–100, по умолчанию 50 |

Ответ: `{total, items}`. Строка содержит:

- `message_id`, `created_at`, `pseudonym`;
- `question` — первые 200 символов, `answer` — первые 200 символов;
- `flags` — список установленных флагов;
- `rating` — `1`, `-1` или `null`;
- `verdict` — `null` или последний вердикт;
- `processing_ms`.

Сортировка: `created_at DESC, id`. Недопустимые значения → 422.

> Уточнение к согласованному дизайну. Фильтр по языку был в эскизе
> экранов. Язык запроса сейчас не сохраняется, поэтому фильтр убран из
> этапа. Его добавление — отдельная колонка и изменение схемы, позже.

### 4.3. `GET /admin/quality/answers/{message_id}`

404 `message_not_found`, если такого ответа ассистента нет.

Ответ:

- `message` — разбираемый ответ: `id`, `created_at`, `content`, `sources`,
  `evidence`, `processing_ms`;
- `conversation` — `{pseudonym, messages: [{id, role, content,
  created_at}]}`, весь диалог;
- `rating` — `{value, comment, updated_at}` или `null`;
- `reviews` — `[{verdict, reasons, note, created_at, reviewer:
  {username}}]`, новые сверху;
- `neighbors` — `{prev_id, next_id}`, соседние ответы в выборке. Выборка
  задаётся теми же query-параметрами, что и в 4.2.

### 4.4. `POST /admin/quality/answers/{message_id}/review`

Тело:

- `verdict`;
- `reasons` — от 0 до 7 элементов, уникальные, только из списка;
- `note` — до 2000 символов, необязательно;
- `reason` — причина для журнала, 3–1000 символов, тот же тип `Reason`,
  что на этапе 2.

Добавляет строку в `answer_reviews` и запись `answer.reviewed` в журнал
(`target_type="message"`, `after` = `{verdict, reasons}`) в одной
транзакции. Сбой записи в журнал откатывает обе. Каждый вызов — новая
запись: правило «повтор ничего не меняет» здесь не применяется, потому что
разметка — это история. Ответ — та же структура, что в 4.3.

### 4.5. `POST /admin/quality/answers/{message_id}/reveal-user`

Тело: `{reason}`. Возвращает `{user_id}`. Пишет в журнал
`user.identity_revealed` (`target_type="message"`, `target_id` = id
сообщения, `after` = `{user_id}`).

### 4.6. `GET /admin/quality/summary?period=7d|30d|90d|all`

Ответ:

- `answers` — число ответов ассистента за период;
- `rated`, `down`;
- `down_share` — `down / rated`, `null` при `rated = 0`;
- `reviewed`, `reviewed_share`;
- `verdicts` — `{correct, partial, wrong}`, считаются по последней
  разметке;
- `reasons` — `{reason: count}`;
- `no_precise_citation_share` — среди ответов с `evidence`;
- `median_processing_ms` — `null`, если данных нет;
- `down_unreviewed` — число 👎 без разметки.

### 4.7. Главная админки

`GET /admin/stats` получает поле `quality: {down_unreviewed}`, данные за
всё время. Блок «Требует внимания» показывает строку, если значение
больше 0.

### 4.8. Журнал

- В `ADMIN_ACTIONS` добавляются `answer.reviewed` и
  `user.identity_revealed`.
- В `TARGET_TYPES` добавляется `message`.
- Схема журнала не меняется.
- Страница `/admin/audit` получает подписи новых действий и типа объекта
  на трёх языках.

## 5. Экраны админки

### 5.1. Лента `/admin/quality`

- Пункт меню «Качество ответов» стоит между «Пользователями» и
  «Обращениями».
- Сводка: пять плиток `StatTile` (доля 👎, размечено, неверных среди
  размеченных, без точной ссылки, медианное время) и переключатель
  периода.
- Быстрые ссылки: «👎 без разметки» (`rating=down&verdict=unreviewed`),
  «Без точной ссылки», «Неверные».
- Фильтры: период, оценка, вердикт, флажки признаков, поиск. Всё хранится
  в URL, как в списке пользователей. Смена фильтра сбрасывает `offset`.
  Недопустимые значения игнорируются.
- Таблица: когда, псевдоним, вопрос, значки признаков, оценка, вердикт.
  Строка — ссылка на разбор, текущая строка запроса передаётся в
  параметре `back`.
- Пустой результат при активных фильтрах: «Ничего не найдено» и сброс.

### 5.2. Разбор `/admin/quality/<message_id>`

- Ссылка «← К ленте» использует `back`, только если он начинается с `?`.
- Кнопки «Предыдущий» и «Следующий» идут по `neighbors` в рамках выборки
  из `back`.
- Левая колонка: диалог в виде переписки, разбираемый ответ подсвечен,
  под ним источники.
- Правая колонка (на телефоне — ниже):
  - «Признаки» — для старых ответов «нет данных»;
  - «Оценка пользователя»;
  - «Разметка»: вердикт (три кнопки), причины (флажки), заметка,
    причина для журнала (обязательная, 3–1000), кнопка «Сохранить
    разметку»; ниже история разметок;
  - «Открыть клиента» — `ConfirmDialog` с обязательной причиной и текстом
    «Действие попадёт в журнал», после успеха переход на
    `/admin/users/<user_id>`.
- Ошибки показываются текстом по коду, как на этапе 2.
- Данные загружаются через `useAdminFetch`, отправка — через `adminSend`
  и `errorText`.

### 5.3. Главная админки

Строка «Ответы с 👎 без разметки: N» в блоке «Требует внимания» ведёт на
`/admin/quality?rating=down&verdict=unreviewed`.

## 6. Сайт: оценка ответа

- Компонент `AnswerRating` стоит под каждым ответом ассистента:
  - в чате на главной (`components/ChatPanel.tsx` и `hooks/useQuery.ts`):
    `message_id` берётся из ответа API;
  - в истории диалога в кабинете
    (`app/account/conversations/[conversationId]/page.tsx`): начальное
    состояние берётся из `rating`.
- Только для вошедших и только если `message_id` есть.
- Поведение:
  - нажатие на 👍/👎 сохраняет оценку сразу, кнопка подсвечена
    (`aria-pressed`);
  - повторное нажатие на ту же кнопку снимает оценку;
  - после 👎 появляется необязательное поле «Что не так?» (до 1000
    символов) с кнопкой «Отправить», которая повторно отправляет PUT с
    `value=-1` и комментарием;
  - подпись: «Спасибо, это поможет улучшить ответы».
- Ошибка (сеть, 429): состояние откатывается к прежнему, рядом короткая
  подсказка. Ответ не блокируется.
- Тексты на RU/KA/EN в существующем словаре сайта (`lib/i18n.tsx`),
  грузинские — по навыку `georgian-writing-style`.
- Стиль — существующие токены сайта, без новых библиотек.

## 7. Политика конфиденциальности

В `frontend/lib/legal-content.ts`, документ privacy, RU/KA/EN:

- «Цели и основания»: добавляется цель — проверка и улучшение качества и
  точности ответов, включая выборочный просмотр вопросов и ответов
  уполномоченным администратором. При разборе личность пользователя по
  умолчанию скрыта, её раскрытие фиксируется в журнале.
- «Какие данные обрабатываем»: добавляются оценки ответов и комментарии к
  ним.
- Обновляется версия документа (`updated`), например «Версия 2026-10-12 ·
  действует с <даты деплоя>». Дату вступления подтверждает Гела.

Формулировки предлагает реализация. Окончательную редакцию утверждает
Гела до мержа. Это условие мержа, а не реализации.

## 8. Тесты

Бэкенд, PostgreSQL (новый `test_admin_quality_postgres.py`, тот же
фикстурный движок с `schema_translate_map`):

- скрипт схемы: план, применение, повторный запуск ничего не меняет,
  контрольная сумма закреплена в `deploy_production.sh`;
- защита `answer_reviews` от UPDATE и TRUNCATE; DELETE возможен только
  каскадом;
- `POST /query` сохраняет `evidence` и `processing_ms` и возвращает
  `message_id`; это проверяется на уровне сохранения с подменённым
  RAG-пайплайном;
- оценка: создание, замена, снятие; чужое сообщение — 404; сообщение
  пользователя — 409; лимит — 429; пустой комментарий сохраняется как NULL;
- лента: каждый фильтр, флаги на граничных значениях (30 000 мс, NULL
  evidence), поиск с экранированием, привязка вопроса к ответу, сортировка,
  `total`;
- разбор: состав, `neighbors` в рамках фильтра, история разметки;
- разметка: запись в журнал, история накапливается, недопустимая причина —
  422, откат при сбое журнала;
- раскрытие: пишет в журнал, возвращает id;
- сводка: доли, `null` при нуле, медиана, `down_unreviewed`;
- псевдоним стабилен, не содержит id, отличается у разных пользователей.

Бэкенд без БД: 403 для не-админа на всех маршрутах `/admin/quality/*`,
401 для гостя на маршрутах оценки.

Фронтенд, Playwright, на моках API:

- лента: фильтры в URL, очередь «👎 без разметки», переход в разбор и
  возврат с сохранением фильтров;
