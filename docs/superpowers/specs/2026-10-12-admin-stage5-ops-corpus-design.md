# Админка, этап 5: операции и корпус — дизайн

Дата: 2026-10-12. Статус: дизайн согласован с Гелой в чате (вариант A,
разбивка 5a/5b, белый список из четырёх задач); на ревью спека.

## Контекст и цель

Ночные задачи InfoHub запускает cron **на хосте** `infohub-production`, а не
бэкенд: скрапер и пост-обработка (`run_scraper.sh`, 03:00 UTC, внутри —
канарейка), бэкап БД (`ops/backup-infohub-db.sh`, 01:30 UTC), restore drill
(`ops/restore-drill-infohub-db.sh`, первая суббота месяца). Их логи и маркеры
лежат в `/root/infohub/logs` и `/root/backups/infohub`, которые в контейнер
бэкенда не смонтированы. Поэтому:

- о сбоях Гела узнаёт только из Telegram-алертов, в админке состояния задач
  нет;
- блок логов на странице «Скрапер» (`GET /admin/ops`) читает файлы, которых в
  контейнере нет, и всегда пуст;
- запустить задачу вне расписания можно только по SSH;
- старый роутер `/api/v1/scraper/start|status|tasks` запускает устаревший
  HTML-краулер `InfoHubScraper` в процессе бэкенда, мимо `flock` хоста.

Этап 5 — последний из пяти (1 основа → 2 клиенты → 4 качество → 3 динамика →
5 операции). Он делится на два PR:

- **5a — только просмотр:** страница «Состояние системы», страница «Корпус»,
  уборка нерабочего старого.
- **5b — ручной запуск:** заявки из админки, диспетчер на хосте, защита.

5b опирается на канал статусов из 5a и ревьюится отдельно, потому что это
единственный новый путь записи из браузера.

### Успех этапа

- На `/admin/system` видно, когда последний раз отработали скрапер,
  канарейка, бэкап и restore drill, чем закончились и что в хвосте лога;
  просроченная или упавшая задача выделена.
- На `/admin/corpus` видно, сколько документов и чанков в базе, сколько
  поступило за 7/30 дней и по неделям, и где пробелы (без даты, без чанков).
- В админке нет блоков, которые всегда пусты, и нет эндпоинтов, запускающих
  работу мимо блокировок хоста.
- (5b) Из админки можно запустить четыре задачи из белого списка; каждый
  запуск журналируется, не пересекается с ночным и не ломает алерты.

### Решения, принятые с пользователем

- Канал «хост ↔ админка» — файлы (вариант A): хост пишет JSON-статусы в
  папку, смонтированную в бэкенд только для чтения; заявки на запуск бэкенд
  кладёт в отдельную папку, которую забирает cron-диспетчер на хосте.
  Бэкенд не получает docker-сокет, SSH или право исполнять что-либо на хосте.
- Схема БД не меняется ни в 5a, ни в 5b.
- Белый список 5b: загрузка новых документов (`--ingest-only`), полный
  ночной прогон, канарейка, бэкап БД. Restore drill — только просмотр.

### Вне этапа 5

- Запуск restore drill, отдельных шагов пост-обработки, бэкфиллов, реиндекса.
- История запусков глубже последнего (только последний статус и последняя
  заявка на задачу).
- Редактирование или удаление документов корпуса из админки.
- Отмена уже идущей задачи.
- Расписание cron из админки.

# Часть 5a — просмотр

## 1. Канал статусов (хост)

### Файл статуса

`/root/infohub/ops-status/<job>.json`, где `job` ∈ `scraper`, `canary`,
`backup`, `restore_drill`:

```json
{
  "schema_version": 1,
  "job": "scraper",
  "started_at": "2026-10-12T03:00:02Z",
  "finished_at": "2026-10-12T03:41:10Z",
  "exit_code": 0,
  "summary": "+3 new docs",
  "trigger": "cron",
  "log_tail": ["...", "..."]
}
```

- `summary` — одна строка итога: для скрапера `+N new docs`, для канарейки
  строка `CANARY: 10/10 ...`, для бэкапа имя и размер дампа, для drill —
  `pass`/`fail` и длительность. Если итог не найден — пустая строка.
- `trigger` — `cron` или `manual` (5b).
- `log_tail` — последние 40 строк лога задачи, каждая обрезана до 300
  символов.

### Запись: `ops/write_job_status.py`

`write_job_status.py JOB STARTED_AT EXIT_CODE SUMMARY LOG_FILE` (trigger и признак пропуска приходят из окружения: `INFOHUB_JOB_TRIGGER`, `INFOHUB_JOB_SKIPPED=1`)

- Проверяет `job` по фиксированному списку, иначе выход 2.
- Хвост лога пропускает через фильтр, который заменяет на `[redacted]`
  значения после `token`, `key`, `secret`, `password`, `Authorization`
  (регистр не важен) и всё, похожее на `bot<digits>:<...>`. Логи уже
  агрегатные; фильтр — вторая страховка.
- Пишет атомарно: JSON собирается на stdlib Python, во временный
  файл в той же папке, затем `mv`. Права: папка `0755`, файл `0644`.
- Никогда не меняет код выхода вызывающего скрипта: ошибки записи статуса
  логируются и проглатываются.

### Подключение к задачам

- `run_scraper.sh`: в начале запоминает `started_at`; `trap ... EXIT`
  пишет статус `scraper` с итоговым кодом выхода и `+N new docs`. Отдельно,
  сразу после канарейки, пишет статус `canary` с `CANARY_EXIT` и строкой
  `CANARY:`. В режиме `--ingest-only` канарейка не запускается и её статус
  не трогается.
- `ops/backup-infohub-db.sh` и `ops/restore-drill-infohub-db.sh`: в
  существующую EXIT-ловушку (там уже вызывается `ops_alert.sh`) добавляется
  вызов `write_job_status.py`. Пропуск из-за занятой блокировки записывается с `skipped: true` (бэкап выходит с 0, drill с 75).
- Скрипты вызывают `write_job_status.py` по пути рядом с собой, так же как
  сейчас вызывают `*_alert.sh`.

### Монтирование и деплой

- `docker-compose.yml`, сервис `backend`:
  `- /root/infohub/ops-status:/app/ops-status:ro`.
- `scripts/deploy_production.sh` до `docker compose up` выполняет
  `install -d -m 0755 /root/infohub/ops-status` (идемпотентно), как сейчас
  ставит cron-файлы.
- Путь в бэкенде задаётся `ADMIN_OPS_STATUS_DIR` (по умолчанию
  `/app/ops-status`), чтобы тесты подставляли временную папку.

## 2. Бэкенд 5a

### `GET /api/v1/admin/system`

Роутер `api/routes/admin_system.py`, `dependencies=[Depends(require_admin)]`.
Логика — `core/admin_system.py` (чтение и вычисление состояния отдельно от
HTTP).

```json
{
  "generated_at": "2026-10-12T17:00:00Z",
  "jobs": [
    {
      "job": "scraper",
      "state": "ok",
      "started_at": "...", "finished_at": "...",
      "exit_code": 0, "summary": "+3 new docs", "trigger": "cron",
      "log_tail": ["..."]
    }
  ]
}
```

Всегда четыре элемента в порядке `scraper, canary, backup, restore_drill`.

`state` вычисляется на сервере:

| state | условие |
|---|---|
| `failed` | `exit_code != 0` и не `skipped` |
| `skipped` | `skipped: true` в файле (бэкап выходит с 0, drill с 75 при занятой блокировке) |
| `stale` | код 0, но `finished_at` старше порога |
| `ok` | код 0 и в пределах порога |
| `unknown` | файла нет, он не читается или не проходит валидацию |

Пороги свежести: скрапер, канарейка, бэкап — 26 ч; restore drill — 36 дней (ежемесячный запуск + запас).
`skipped` тоже становится `stale`, если старше порога.

Файл читается с лимитом 64 КБ; невалидный JSON, неизвестный
`schema_version` или чужой `job` → `unknown` без 500. Поля, которых нет, —
`null`.

### `GET /api/v1/admin/corpus`

Роутер `api/routes/admin_corpus.py`, логика `core/admin_corpus.py`. Только
SQL-чтение.

```json
{
  "totals": {
    "documents": 14725, "chunks": 269218,
    "added_7d": 12, "added_30d": 61,
    "last_ingest": "2026-10-12T03:12:40Z"
  },
  "by_type": [
    {"document_type": "law", "documents": 512, "added_30d": 3,
     "without_date": 0, "without_chunks": 1}
  ],
  "weekly": [
    {"week_start": "2026-07-27", "added": 9, "partial": false}
  ],
  "pending": {"decision_facts": 4, "law_amendments": 0}
}
```

- `added_*`, `last_ingest`, `weekly` — по `documents.created_at`.
- `weekly` — 12 недель с понедельника по времени Тбилиси, последняя неделя
  `partial: true`; используется тот же помощник границ окон, что в
  `core/admin_trends.py` (переиспользуется, не копируется).
- `without_date` — `date_published IS NULL`; `without_chunks` — нет строк в
  `document_chunks` (`NOT EXISTS`, индекс `idx_chunks_document`).
- `by_type` отсортирован по `documents` убыванию.
- `pending` — те же счётчики, что сейчас отдаёт `/admin/ops`
  (функция из `admin.py` переносится в `core/admin_corpus.py`).

### Уборка бэкенда

# Часть 5b — ручной запуск

## 6. Заявка из админки

### `POST /api/v1/admin/system/jobs/{job}`

`job` ∈ `scraper_ingest`, `scraper_full`, `canary`, `backup` (enum в пути;
иное → 422). Тело пустое.

Порядок:

1. Проверки (ниже) → при нарушении 409 с машинным `code` и человеческим
   `detail`.
2. Атомарно (tmp + `os.replace`) пишется
   `/app/ops-requests/<job>.json`:
   `{"schema_version":1,"request_id":"<uuid4>","job":"<job>","requested_at":"...","actor_id":"<uuid>"}`.
3. В той же транзакции БД пишется `admin_audit_log` с
   `action = "ops.job_requested"`, `target_type = "ops_job"`,
   `target_id = <job>`, данные — `request_id`.
4. Если коммит журнала не удался — файл заявки удаляется, ответ 500.

Ответ 202: `{"request_id": "...", "job": "...", "state": "queued"}`.

### Проверки (409)

| code | условие |
|---|---|
| `already_pending` | файл заявки на эту задачу уже лежит, или статус заявки `queued`/`running` |
| `scraper_busy` | для `scraper_ingest`/`scraper_full`: есть активная заявка на другую скрапер-задачу |
| `backup_too_recent` | `backup`: последний успешный бэкап моложе 6 ч; `detail` содержит время |
| `canary_too_recent` | `canary`: последний запуск канарейки моложе 10 мин |

Проверки — защита от двойного клика и случайностей, а не от гонок: настоящую
взаимоисключаемость обеспечивают `flock` на хосте.

### Монтирование

`- /root/infohub/ops-requests:/app/ops-requests` (чтение и запись) — единственная
папка хоста, куда бэкенд пишет. `deploy_production.sh` создаёт её
(`install -d -m 0770`). Путь — `ADMIN_OPS_REQUEST_DIR`.

## 7. Диспетчер (хост)

`ops/ops-dispatcher.sh`, cron `* * * * *` из нового
`ops/cron-infohub-ops-dispatcher` (ставится `deploy_production.sh`, как
остальные cron-файлы). Свой `flock -n` на `/run/lock/infohub-ops-dispatcher.lock`:
пока идёт одна задача, следующие минуты просто выходят, заявки ждут.

Для каждого файла в `ops-requests/`, по возрастанию времени изменения:

1. Имя должно быть ровно одним из `scraper_ingest.json`, `scraper_full.json`,
   `canary.json`, `backup.json`; иначе файл переносится в
   `ops-requests/rejected/` и пропускается.
2. Из файла читается только `request_id`, проверяется как UUID
   (`python3`, без `eval`); невалидный → `rejected/`.
3. Файл переносится в `ops-requests/processing/`, в
   `ops-status/<job>.request.json` пишется `queued → running` с
   `request_id`, `started_at`.
4. Команда выбирается жёстким `case` по имени файла:
   - `scraper_ingest` → `INFOHUB_JOB_TRIGGER=manual run_scraper.sh --ingest-only`
   - `scraper_full` → `INFOHUB_JOB_TRIGGER=manual INFOHUB_MANUAL_RUN=1 run_scraper.sh`
   - `canary` → `docker exec infohub-backend python /app/scripts/canary_eval.py`
     с тем же разбором и `canary_alert.sh`, что в ночном прогоне (вынести в
     `ops/run_canary.sh`, ночной `run_scraper.sh` вызывает его же)
   - `backup` → `INFOHUB_JOB_TRIGGER=manual ops/backup-infohub-db.sh`
5. Итог в `<job>.request.json`: `done` (код 0), `skipped` (скрапер вышел с
   «Another scraper run is active» или `skipped: true`), `failed` (иное);
   `finished_at`, `exit_code`. Файл из `processing/` удаляется.
6. Если диспетчер упал посреди задачи, при следующем запуске файл в
   `processing/` старше 6 ч помечается `failed` с `reason: "interrupted"`.

`INFOHUB_JOB_TRIGGER` прокидывается в `write_job_status.py` как `trigger`.

## 8. Защита задач

- **Скрапер:** ручной и ночной запуск делят `flock` в `run_scraper.sh`;
  занятый замок → `skipped`.
- **Полный прогон:** при `INFOHUB_MANUAL_RUN=1` `scraper_alert.sh` не
  меняет счётчик `zero_new_streak` (не увеличивает и не сбрасывает); алерт
  при ошибке или `?` отправляется как обычно.
- **Бэкап:** серверная проверка 6 ч (§6); в диалоге подтверждения —
  «Хранится 4 последних дампа; самый старый будет удалён». Своя блокировка
  бэкапа (`/run/lock/infohub-db-backup.lock`) остаётся.
- **Канарейка:** не чаще раза в 10 мин; около 10 вызовов gpt-4o-mini.
- Telegram-алерты не меняются: задачи запускаются теми же скриптами.

## 9. Бэкенд и фронтенд 5b

- `GET /admin/system` дополняется полем `request` у каждой задачи — содержимое
  `<job>.request.json` (`state`, `request_id`, времена) и признаком
  «заявка лежит, диспетчер ещё не взял» (`state: "queued"`). Для
  `scraper_ingest`/`scraper_full` заявка показывается на карточке скрапера.
- На карточках кнопки: скрапер — «Загрузить новые документы» и «Полный
  ночной прогон»; канарейка — «Прогнать канарейку»; бэкап — «Бэкап сейчас»;
  у restore drill кнопки нет.
- Каждая кнопка открывает диалог подтверждения с описанием цены (время,
  LLM-вызовы, ротация дампов). После 202 карточка показывает «В очереди»,
  затем «Выполняется с HH:MM», затем итог; пока заявка активна, страница
  перечитывает статус каждые 15 с, кнопки задачи отключены.
- Ответ 409 показывается текстом `detail` в карточке.

## 10. Тесты 5b

- Бэкенд: enum задач (422), каждая строка таблицы 409, атомарность «файл +
  журнал» (сбой коммита → файла нет), 202 пишет корректный JSON, 403 для
  не-админа.
- `ops/tests/test_ops_dispatcher.sh`: команды подменены заглушками через
  переменные окружения; посторонний файл → `rejected/`, невалидный UUID →
  `rejected/`, занятый замок → `skipped`, успех → `done`, падение → `failed`,
  зависший `processing/` → `interrupted`, `INFOHUB_JOB_TRIGGER=manual`
  доходит до статуса.
- `scraper_alert.sh` с `INFOHUB_MANUAL_RUN=1` не трогает файл счётчика.
- e2e: кнопки и диалоги, переходы `queued → running → done` на моках, 409,
  отсутствие кнопки у drill; визуальный эталон карточек с кнопками.

**Отклонения при реализации.**

1. Тесты shell-скриптов лежат в pytest (`backend/tests/test_ops_dispatcher.py`, `test_ops_run_canary.py`)
   по образцу `test_db_backup_policy.py`, а не в `ops/tests/*.sh`.
2. Текст 409 локализуется по `code` (соглашение этапа 2), поэтому время бэкапа в сообщение не
   повторяется; карточка и так показывает время последнего бэкапа.
3. Недоступная для записи папка заявок даёт 500 с кодом `ops_queue_unavailable`.
4. Строка журнала сбрасывается (flush) до записи файла.
5. `processing/` и `rejected/` лежат не в `ops-requests/`, а в каталоге только для root
   `/var/lib/infohub/ops-dispatch` (0700, `INFOHUB_OPS_DISPATCH_STATE`, создаёт deploy). Бэкенд пишет в
   `ops-requests/`, и он не должен управлять каталогами, куда root переносит файлы (атака через
   симлинк). Диспетчер сначала переносит заявку в `processing/` и проверяет уже перенесённую копию.
6. Список очереди разделяется NUL. Имя файла, не совпадающее с одним из четырёх имён задач, уходит в
   `rejected/`, если состоит только из `[A-Za-z0-9_.-]`, иначе удаляется.
7. Бэкенд не читает никакой `processing/`: «выполняется» берётся только из
   `ops-status/<job>.request.json`, который диспетчер пишет сразу после взятия заявки.
8. Файл заявки на хосте открывается с `O_NOFOLLOW|O_NONBLOCK` и принимается только как обычный файл
   не больше 4 КиБ.
9. KA-строки вычитаны по скиллу грузинского стиля; для бэкапа оставлен уже принятый в админке термин «სარეზერვო ასლი».
10. `ops_request.py` не открывает путь из аргументов: файл заявки он собирает сам из
    `<state>/processing` и имени задачи из списка (другой каталог — отказ), а вывод задачи получает
    на stdin. Так закрыто замечание SonarCloud о path traversal.

## 11. Деплой 5b

Обычный `deploy.sh`: создаёт `ops-requests`, ставит cron диспетчера,
пересоздаёт бэкенд с вторым монтированием. Проверка после деплоя — Гела
нажимает «Прогнать канарейку» и в течение 1–2 минут видит
`running`, затем `done` и свежий статус канарейки.

## Риски

- **Права в смонтированной папке.** `backend/Dockerfile` не задаёт `USER`,
  процесс бэкенда — root, поэтому `ops-requests` с `0770 root:root`
  достаточно. Если `USER` когда-нибудь появится, права папки нужно будет
  выдать этому uid.
- **Скрипты хоста не деплоятся образом.** `run_scraper.sh`, `*_alert.sh` и
  `ops/` лежат в репозитории и обновляются `git reset --hard` в
  `/root/infohub` при `deploy.sh`; cron вызывает именно
  `/root/infohub/run_scraper.sh`. Новый диспетчер и `write_job_status.py`
  доставляются тем же путём.
- **Ночной прогон во время деплоя.** `git reset` может заменить
  `run_scraper.sh`, пока он выполняется; bash читает скрипт по ходу. Риск
  существовал и раньше; деплой 5a/5b не делать около 03:00–04:00 UTC.
- **Пустое состояние после деплоя 5a** — ожидаемо, описано в §5.
