# InfoHub ingestion freshness audit — 2026-08-24

## Итог

Счётчик `15 140` не означает, что nightly scraper остановился. Cron запускался
ежедневно и завершался с кодом `0`. В период 20–22 августа база выросла на 15
документов; в запусках 23 и 24 августа источник на момент проверки не отдавал
новых пригодных документов. После запуска 24 августа официальный API показал
ещё одну новую запись `NewDocument`, поэтому её должен подобрать следующий
обычный цикл ingestion.

Отдельно обнаружены 60 ранее не сохранённых карточек вида `Bill`. Их detail API

являются пригодными юридическими документами для RAG и корректно пропускаются,
но старый лог ошибочно называл их «new this page» даже при `store() -> None`.

## Исправление наблюдаемости

- scraper теперь отдельно считает `known`, `unseen`, `ingested`,
  `skipped_short`, `detail_failures` и `processing_errors` для каждого species;
- машинная строка `INFOHUB_INGEST_SUMMARY=` показывает source total и реальный
  результат сохранения, не смешивая найденные карточки с добавленными
  документами;
- public health добавляет `last_document_ingested_at`, `documents_last_24h` и
  `documents_last_7d` рядом с общим количеством;
- тяжёлая инициализация embedding/pgvector перенесена на storage path, чтобы
  диагностика каталогов не требовала загрузки модели и подключения к векторной
  базе.

## Интерпретация метрики

`total_documents` — накопительный размер локального корпуса, а не счётчик
публикаций официального сайта. Он растёт только когда одновременно выполнены
три условия: источник опубликовал ещё не известную карточку, detail API вернул
содержательное тело и запись успешно прошла сохранение/чанкинг. Поэтому нулевой
дневной прирост сам по себе нормален; проблемой считается устаревший
`last_document_ingested_at` вместе с ненулевым `unseen`, ошибками detail/storage
или отсутствующим nightly-запуском.

## Ограничения

Это operational, а не юридическая оценка пустых Bill-карточек. Они не будут
искусственно превращаться в документы без официального текста. Если InfoHub
позже наполнит те же UUID содержанием, безопасный incremental scan увидит их
как `unseen` и повторит проверку.
